# 1. 项目概述

## 1.1 项目背景

本项目构建一套 **二轴惯性/视觉复合稳定跟踪转台**，打通
**MCU 实时电机控制 + 惯性增稳 + 无线手柄交互 + Linux 视觉推理** 的完整技术链路。

系统有两层技术内核：

1. **差速齿轮机构**：两个闭环步进电机通过齿轮驱动**同一托盘**，构成
   **差速（differential）二轴转台**。单个电机无法独立决定托盘姿态，
   托盘姿态由两个电机转角的**组合**决定 —— 这是本项目所有运动学解算的出发点。
2. **复合稳定**：**惯性稳定环**（IMU 陀螺反馈，100 Hz）负责抵消载体扰动、
   保持视轴指向；**视觉跟踪环**（目标偏差，低频）负责锁定目标。
   两环分工、各司其职 —— 这是光电转台/吊舱的标准架构。
   ⚠ 本方案的惯性环受 IMU 模块回报率限制只到 100 Hz，两环带宽分离度不大（见 1.3 与 4.4）。

项目性质为**个人技术项目，面向 2027 年秋季招聘**，因此除功能实现外，
设计决策的可解释性与工程取舍同样重要（见第 6 章）。

## 1.2 项目目标

项目分三期推进，每期都可独立演示，后一期在前一期基础上叠加：

| 期 | 目标 | 依赖硬件 | 状态 |
|---|---|---|---|
| **一期** | **手柄无线操控 + 惯性增稳**（手动模式，视轴抗扰） | ESP32-S3 + CAN 收发器 + 手柄 + **IMU** | 本次重点 |
| **二期** | 泰山派视觉识别目标 → 串口下发偏差 → 视觉伺服跟踪（自动模式） | 一期 + 泰山派 + 摄像头 | 路线已定，暂不展开 |
| **三期** | **手柄找目标 → 按键切自动跟踪 → 再按键回手动** | 全部 | 路线已定，暂不展开 |

**一期内部有两个可演示节点**，便于控制节奏：

| 节点 | 内容 | 价值 |
|---|---|---|
| 节点 A（M1–M5） | 手柄操控云台转动 + 安全限位 | 已经是一个完整的"无线操控云台"演示 |
| 节点 B（M6–M7） | 叠加惯性增稳，成为"稳定跟踪转台" | **名称里的"惯性复合稳定"在此兑现** |

> **一期不需要泰山派，也不需要摄像头。** 这是刻意的设计：先把
> "手柄 → ESP32 → CAN → 电机 → 机械" 这条最底层的链路彻底跑通、标定准确，
> 再叠加增稳，最后才叠加视觉。视觉模型训练、泰山派环境搭建全部推到二期。

## 1.3 设计原则

1. **带宽分层**：三层控制回路按带宽分层 —— 电机内部环（20 kHz）≫ 速率稳定环（100 Hz）> 指向环（30 FPS）。**内环必须远快于外环**，否则外环的相位滞后会让系统振荡。⚠ **注意：本方案里稳定环与指向环只差约 3 倍（100 Hz vs 30 Hz），不满足"远快于"，这是 v1.2 修正 IMU 接口后暴露出的结构性问题**，应对方式见 4.4。
2. **实时性分层**：ESP32 承担全部硬实时控制；泰山派只下发高层意图，其卡顿或掉线不得影响运动安全。
3. **失联安全**：手柄掉线、IMU 异常、泰山派掉线、CAN 无响应 → 按预设安全策略停机（见 2.3）。
4. **先标定后闭环**：机械相关的一切（方向符号、镜像、零位、行程、**回程间隙**）必须先实机标定写入配置，再谈闭环。**增稳环增益必须在限位与急停就绪之后才允许调试**。
5. **可标定**：所有机械与传感器相关系数（镜像、限位、陀螺零偏、标度因数、稳定环增益）均为可配置参数，不在代码里写死。
6. **分层可测**：通信协议、运动学解算、手柄解析、IMU 采集、稳定环五部分可独立测试，互不阻塞。
7. **视觉解耦**：识别算法与"视觉→控制"链路分离，先用手工特征（色块/形状）跑通链路，后续替换为训练模型时链路代码不改。

## 1.4 项目范围

**包含**：硬件选型与接线、ESP32 固件（ESP-IDF + CAN 协议栈 + 运动学 + 惯性增稳 + 手柄 + 安全）、
泰山派侧应用（取流 + 识别 + 通信）、系统联调与测试、标定与文档。

**不包含**：结构件重新设计加工、电机内部固件开发、云端服务、滑环机构加工（若自转范围需要）。

### CAN 总线负载估算（v1.2 后已不再是约束）

v1.1 时增稳环计划跑 500 Hz–1 kHz，**CAN 带宽是硬约束**，位置模式在 1 kHz 下会爆总线（120%）。
v1.2 按实物把增稳环降到 **100 Hz** 后，总线占用掉了 5–10 倍，**这个约束消失了**：

| 下发方式 | 单周期帧数 | 数据长度 | @100 Hz |
|---|---|---|---|
| 位置模式 `FD`（2 包/电机） | 4 帧 ≈ 600 bit | 12 B | 60 kbps（**12%**）✅ |
| 快速位置模式 `F1`/`FC` | 2 帧 | 11 B / 6 B | 约 5% ✅ |
| **速度模式 `F6`（1 帧/电机）** | **2 帧 ≈ 260 bit** | **7 B** | **26 kbps（5.2%）**✅ |

> 扩展帧按最坏位填充估算约 130 bit/帧；速度模式数据含 7 字节（功能码+方向+速度2B+加速度1B+同步1B+校验1B）。

**结论**：

- 一期采用**速度模式 `F6`，100 Hz 下发，总线负载 5.2%**，余量极大
- ⚠ **但选速度模式的理由已经不再是总线带宽** —— 位置模式在 100 Hz 下只占 12%，完全可行。
  真正的理由变成了**控制结构**（速率语义 + 相位裕度），详见 6.8。
  **这是 v1.2 相对 v1.1 最重要的论证变更：不要再引用"位置模式爆总线"这个已经失效的论据。**
- 速度模式**不需要多机同步广播** —— 速度指令立即生效，两帧背靠背发出
  在时间上足够接近（< 0.5 ms），远小于 10 ms 周期，无需 `FF 66` 触发
- 位置模式保留给**低频绝对定位**（回零后的精确指向、漂移校正），不与增稳环同频运行

## 2.3 安全需求

| 编号 | 需求 | 触发条件 | 动作 |
|---|---|---|---|
| SR-01 | 手柄失联保护 | 超过 500 ms 未收到手柄 notify 帧（或 BLE 断开） | MANUAL 模式下立即停机（速度归零） |
| SR-02 | 泰山派失联保护 | 超过 500 ms 未收到心跳 | AUTO 模式下降级为惯性稳定保持（若 IMU 正常）或 IDLE |
| SR-03 | CAN 无响应保护 | 连续 N 次状态读取无应答 | 停机 + RGB 报警 |
| SR-04 | 软限位 | 自转/俯仰角超出行程范围 | 立即停止该方向运动并报警 |
| SR-05 | 全局急停 | 手柄**急停组合键 L1+R1+Start** / 板载 BOOT 键 | 任意模式下立即停机，需显式复位。⚠ **Home 键禁用**（长按 3 s 会关手柄电源） |
| SR-06 | 故障处理 | 电机堵转/过流/过热/低压标志置位 | 停止对应电机并上报 |
| SR-07 | 指令校验 | CAN 帧校验错、串口 CRC 错 | 丢弃该帧并计数，连续错误报警 |
| SR-08 | 上电安全态 | 上电 / 复位 | 保持失能，等待显式使能 |
| SR-09 | 掉电保护 | 电源跌落 | 电机失能（电流归零），避免意外运动 |
| **SR-10** | **IMU 数据异常保护** | 陀螺超量程 / **连续丢帧或校验和连续错误** / 零偏突变 / **UART 帧超时** | **稳定环自动降级为旁路（退回纯指向控制）+ 报警**，绝不带着坏数据闭环 |
| **SR-11** | **增稳环自激保护** | 稳定环输出持续饱和或振荡检测触发 | 增益自动回退 + 报警 |
| **SR-12** | **增稳环使能前置条件** | 请求开启增稳环 | 必须已通过软限位标定与急停测试，否则拒绝使能 |

> **必须按顺序实现的安全项**：SR-04 软限位、SR-05 急停、SR-08 上电安全态
> **必须先于增稳环**（SR-12）。增稳环是高增益闭环 —— 一个自激的稳定环
> 会让云台疯狂抖振，**在限位和急停还没就绪时绝不允许上电调试增益**。

## 2.4 非功能需求

- 代码按 ESP-IDF 组件划分，接口清晰、模块解耦
- 所有机械与传感器参数集中在单一配置文件，不散落在业务代码里
- 关键设计决策有文档记录（见第 6 章）
- **实时路径上不使用动态内存分配**（稳定环、CAN 下发、IMU 读取）
- 中文注释与文档
- 可通过串口日志复现任何一次异常

> 不能靠假设。

> **为什么接受这个模块，而不是去买裸 ICM-42688 走 SPI**：
> ① 实物已有，且模块已做完姿态融合与出厂校准，省掉整套 IMU 驱动与标定环节；

> ③ 代价是**采样率被锁死在 100 Hz，增稳带宽天花板降到 ~10 Hz**。

### 3.1.3 CAN 收发器（唯一需要采购的关键件）

ESP32-S3 芯片内部有 **TWAI**（CAN 2.0 控制器），但它只输出逻辑电平 TX/RX，
**必须外接 CAN 收发器芯片**才能接入电机总线。现有 `ZDT_CANable` 是 **USB 适配器**，
无法接到 ESP32 上。

采购要求：

- 收发器类型：**3.3V 供电**（SN65HVD230 首选；TJA1051T/3 亦可）
- ❌ **不要买 MCP2551**（5V 供电，与 ESP32 电平不兼容，需额外电平转换）
- 板载 120 Ω 终端电阻的模块更省事（视总线拓扑决定是否启用）

## 3.2 ESP32-S3 引脚分配

| 功能 | 引脚 | 说明 |
|---|---|---|
| TWAI_TX | GPIO4 | 接 CAN 收发器 TXD |
| TWAI_RX | GPIO5 | 接 CAN 收发器 RXD |
| **IMU UART1_TX** | **GPIO17** | → 模块的 **R**（模块 RX） |
| **IMU UART1_RX** | **GPIO18** | ← 模块的 **T**（模块 TX） |
| 原 SPI 引脚 | GPIO10/11/12/13/14 | **已全部释放**（v1.1 曾给 IMU SPI）。GPIO12/13/14 目前空出备用 |
| 泰山派 UART2_TX | GPIO10 ⬜待上板确认 | → 泰山派 RX（二期，复用原 SPI 引脚） |
| 泰山派 UART2_RX | GPIO11 ⬜待上板确认 | ← 泰山派 TX（二期） |
| 板载 RGB (WS2812) | GPIO48 | 状态指示，无需接线 |
| 板载 BOOT 按键 | GPIO0 | 本地急停 / 模式切换备用 |
| UART0 (GPIO43/44) | — | 调试日志，保留 |

> **为什么把 UART1（GPIO17/18）给 IMU，而把泰山派挪到 UART2**：
> UART1 有 **IO_MUX 默认引脚**，路由最短、延迟最确定。IMU 是**一期就常驻运行、
> 且直接进控制回路**的设备，优先给它；泰山派链路是二期、30 FPS、端到端预算 150 ms，
> 走 GPIO Matrix 多出来的那点延迟完全可忽略。**把确定性留给最需要的一方。**
>
> ⚠ GPIO10/11 是否与板载 Flash/PSRAM 冲突**必须上板确认**（已避开 26–32，
> 33–37 另需确认）—— 见 Q-15、Q-25。

**ESP32-S3 必须避开的引脚**（厂商文档 + 硬件常识）：

- **GPIO26–GPIO32**：板载 Flash / PSRAM 专用，**不可用作普通 IO**，否则系统崩溃
- **GPIO19 / GPIO20**：原生 USB（若启用 USB CDC 则占用）
- **GPIO0 / GPIO45 / GPIO46**：strapping 引脚（GPIO0 拉低进下载模式；板载已有 ISP 一键下载电路）
- **ADC2**（GPIO8–15、45、46）：WiFi/BLE 开启时不可用（本项目不用 ADC）
- ⚠ **GPIO33–GPIO37**：8 MB **Octal PSRAM** 可能占用这几根线（厂商文档只列了 26–32，
  但 Octal PSRAM 通常额外占用 33–37）。**上板前用万用表/原理图确认**，本项目已避开这几根

### 3.3.2 供电方案：12 V 电池

X42S 供电范围 **10–29 V**（标准版），目标使用 **12 V 电池**，可行。注意：

| 电池类型 | 电压区间 | 结论 |
|---|---|---|
| 3S LiPo | 满 12.6 V → 放空 9.0 V | ⚠ **需限制放电深度**，放到 9 V 会低于电机 10 V 下限触发低压保护。建议截止 3.5 V/cell（≈10.5 V） |
| 4S LiFePO4 | 10.0 → 14.6 V（标称 12.8 V） | ✅ 最合适 |
| 铅酸 12 V | 放空 10.5 V → 浮充 13.8 V | ✅ 可用，但重、放电倍率低 |

**12 V 相比 24 V 的两个影响**：

1. **高速扭矩下降**：步进电机供电电压越低，高速时电流爬升越慢、扭矩衰减越早。
   本项目转台为低速低负载工况，影响可忽略；仅在快速大角度甩头时可能出现跟随误差增大。
   ⚠ **但对增稳环要留意**：增稳需要在扰动瞬间快速反向纠偏，对瞬时扭矩有要求。
   若发现增稳响应"发软"，优先怀疑 12 V 供电下的扭矩不足。
2. **电流翻倍**：同功率下 12 V 电流是 24 V 的 2 倍，电池放电能力需匹配。

**电流不需要估算，直接测**：`python tools/zdt_can.py status` 会读回
**总线电压**与**相电流**。让转台跑起来（尤其是增稳环工作、频繁纠偏时）看实际电流。

**供电接线要点**：

- 电机用 12 V 直接供电（X42S 为高压版保护，注意电源纹波）
- ESP32-S3、泰山派、**IMU 模块**都经 **DC-DC 降压到 5 V** 供电
- ⚠ **IMU 模块要 5 V，不是 3.3 V**（见 3.1.2）。板上要有 5 V 轨给它，
  且**不要拿 3.3 V 去试** —— 低于 4.5 V 不在规格内
- **全系统必须共地**：ESP32 GND ↔ CAN 收发器 GND ↔ IMU GND ↔ 电机电源 GND
- DC-DC 为开关电源，**输出噪声不要串到 CAN 线或 IMU 的信号/电源线上**：
  模块远离信号线，输出端加 LC 滤波
- 电机电源入口建议加 **5 A 慢速保险丝**，防止反向/短路
- 电池加防反接（或使用带保护板的电池）

### 3.3.3 CAN 总线接线要点

- **CAN_H / CAN_L 不能接反**（接反表现为完全无通信）
- **总线两端各一个 120 Ω 终端电阻**（即最远两个节点处），不要在中间节点加
- CAN_H/CAN_L 使用**双绞线**，与电机动力线**分开走线**，避免斩波噪声耦合
- 收发器与 ESP32 之间 TX/RX 走短线；收发器的 3.3 V 就近去耦（100 nF + 10 µF）
- **必须有共地**

### 3.3.4 IMU 布线要点（新增，容易踩坑）

- **4 根线跨关节**：`5V` / `GND` / `TXD` / `RXD`，线数是本节最脆弱的一环，
  尤其是**跨越旋转关节的那一段**
- **交叉接**：模块 `TXD` → ESP32 的 **RX**，模块 `RXD` → ESP32 的 **TX**，
  5V 与 GND 一一对应。接反了表现为"一个字节都收不到"
- **逻辑电平 3.3 V，可直连**，不需要电平转换；但**供电必须 5 V**（见 3.1.2），
  别把供电和电平搞混 —— 这是最容易烧模块的一步
- 建议**用成品屏蔽排线或双绞+GND 间隔**的方式走线
- 波特率 115200 已由协议固定（见 3.1.2），**没有"先低频跑通再提速"这一步**；
  要排查链路质量，看的是**丢帧率与校验错误率**，不是降压重试
- 模块是**主动上报**的，ESP32 只管收 —— 没有主机发起的读时序，
  所以不存在"读时序被拉长导致读到旧数据"的问题；但反过来，
  **帧一旦丢掉就是真的丢了**，不会自动重发，必须由固件检测出来
- 若线缆要跨越旋转关节，**务必做应力释放**，并且在固件里实现对
  **帧超时与校验和失败**的检测与计数（对应 SR-10）—— 线断了/读数错了必须能被
  检测到并降级（进安全状态），而不是拿着垃圾角度继续闭环
- IMU 的 GND 与 ESP32 的 GND 要**单点良好连接**，避免地环路；
  `5V` 与 `GND` 建议**成对走线**，减小供电回路的环路面积

## 3.4 机械结构与运动学

### 3.4.1 结构描述

```
              齿轮托盘（上方，20 齿 × 2）  ← IMU 装在这里
            ↗                          ↖
        齿轮                          齿轮
          │                            │
    ══════╪═══ 连接轴承（只传动力）════╪══════
          │                            │
        齿轮(20齿)                   齿轮(20齿)
          │                            │
       电机 1                        电机 2
                   底座（固定）
```

- 两个电机固定在底座上，各带一个 20 齿齿轮
- 两个电机齿轮通过**连接轴承**把动力传到托盘上的两个 20 齿齿轮
- 托盘姿态由**两个电机转角的组合**决定
- **IMU 与摄像头固定在托盘（载荷）上**，随载荷一起运动

### 3.4.2 运动学关系（已实机验证）

设：

- `θ1`、`θ2`：电机 1、电机 2 的机械转角（度）
- `i`：齿轮传动比，本结构 **`i = 1`**
- `pan`：托盘自转角（水平旋转）
- `tilt`：托盘俯仰角（**向上为正**，已确认）

**正解（电机角 → 托盘姿态）**：

```
pan  = (θ1 − θ2) / (2 · i)
tilt = (θ1 + θ2) / (2 · i)
```

**反解（托盘姿态 → 电机角）**：

```
θ1 = i · (tilt + pan)
θ2 = i · (tilt − pan)
```

**速度域（增稳环与手柄速度控制直接使用）**：

```
ω1 = ω_tilt + ω_pan
ω2 = ω_tilt − ω_pan
```

> **重要**：增稳环输出的是托盘的期望角速度 `ω_pan`、`ω_tilt`，
> **落地时复用同一套差速反解**，不需要为增稳单独设计运动学。

### 3.4.3 ⚠ 2 号电机镜像安装（本项目最关键的机械坑）

**实测确认（2026-09-16）**：2 号电机是镜像安装的。给它下发与 1 号**相同方向**的命令，
机构上得到的是**相反方向**。

**不加镜像补偿的后果**：下发"俯仰"命令 → 转台**自转**；下发"自转"命令 → 转台**俯仰**。
两轴完全互换。

**补偿方式**：把 2 号电机的命令**取反**。修正后的命令关系为：

```
ω1_cmd = ω_tilt + ω_pan
ω2_cmd = ω_pan − ω_tilt          ← 注意符号：这是取反后的结果
```

验证（自洽性检查）：

| 工况 | 计算结果 | 机构表现 | 是否正确 |
|---|---|---|---|
| 纯俯仰（ω_pan = 0） | ω1 = +ω_tilt，ω2 = −ω_tilt | 两电机命令相反，但 2 号镜像 → **机构世界同向** → 俯仰 | ✅ |
| 纯自转（ω_tilt = 0） | ω1 = +ω_pan，ω2 = +ω_pan | 两电机命令相同，但 2 号镜像 → **机构世界反向** → 自转 | ✅ |

**标定方法**：`tools/gimbal.py --tilt 45 --rpm 15 --once` 单程停住，观察转台是"俯视/仰视"
（俯仰轴）而不是"转向"（自转轴）。`gimbal.py` 中 `--mirror 2` 默认开启，等价于上述补偿。

> **注意**：小幅来回运动（如 `--tilt 15`）会跑完回原点、位置读数不变，
> **看位置读数查不出有没有动过**。必须用 `--once` 单程停住才能确认。

### 3.4.4 传动比与分辨率

- 传动比 1:1，电机转 1° → 托盘转 1°（理想情况）
- 电机默认 16 细分，**3200 脉冲/圈** → 单脉冲对应 **0.1125°（1.96 mrad）**
- 电机控制精度 < 0.08°，优于单脉冲分辨率
- 托盘姿态理论分辨率 ≈ 0.1125°（实际受齿轮回程间隙限制）

换算：`脉冲数 = 角度 × 3200 / 360`（30° ≈ 267 脉冲）

> **注意**：单脉冲 1.96 mrad 是**视轴稳定精度的理论下限之ー**。
> PR-13 定的 10 mrad 目标，相当于约 5 个脉冲，主要留给回程间隙。

### 3.4.5 IMU 安装位置（决定增稳架构）

> **决策已定（2026-09-17 用户确认）：IMU 装在托盘（载荷）上，贴近摄像头。**

| 方案 | 测到的物理量 | 效果 | 结论 |
|---|---|---|---|
| **装在托盘（载荷）上，贴近摄像头** | **载荷自身的角速率** | 直接反馈稳像，精度最高；真实光电转台的做法 | ✅ **采用** |
| 装在底座（固定件）上 | 载体扰动的角速率 | 需结合关节角推算载荷姿态 → 只能做**前馈**，精度差 | ❌（可作为 6.7 的增强项） |

**为什么必须贴近摄像头**：IMU 离转轴越远，托盘旋转时的**切向加速度与离心加速度**
在 IMU 处的幅值越大，会污染陀螺/加速度计读数（杠杆臂效应）。IMU 与视轴尽量共位，
测到的才最接近视轴真实运动。

**⚠ 代价：线缆要跨旋转关节**。601 模块走 **UART，只需 4 根线**
（`5V` / `GND` / `TXD` / `RXD`，见 3.3.4）走到旋转部件上 ——
比 v1.1 设想的 SPI（6 根）**少 2 根**，这是换用串口模块的一个实际收益。
自转时线缆仍会扭，可选方案：

| 方案 | 说明 | 代价 |
|---|---|---|
| **限制自转角度范围**（如 ±90°） | 最简单，无需额外硬件 | 自转范围受限 |
| **走中空轴** | 利用中间连接轴承（如果是中空的） | 取决于现有结构 |
| **滑环（slip ring）** | 可连续旋转 | 需采购，增加成本与噪声 |
| **把 IMU 装在底座** | 无走线问题 | 退化为前馈方案，精度下降 |

> **建议**：一期先用**限制自转范围**（如 ±90°）的方案验证增稳效果，
> 这不需要任何新硬件。若后续要做连续自转再考虑滑环。
> 注意这与 6.7 的"IMU 装托盘"决策配套 —— 是**为了走线而限制行程**，
> 不是"因为走线难所以放弃托盘方案"。

### 3.4.6 机械约束（待标定）

|---|---|---|
| 自转范围 | 受线缆、结构、IMU 走线限制 | ⬜ 待标定（建议先 ±90°） |

# 4. 软件架构

## 4.1 ESP32-S3 侧（ESP-IDF）

### 4.1.1 软件分层

```
┌──────────────────────────────────────────────────────────────────┐
│ 交互层  │ BLE 手柄解析 / RGB 状态指示 / UART 与泰山派通信          │
├──────────────────────────────────────────────────────────────────┤
│ 决策层  │ 模式状态机（IDLE/MANUAL/AUTO）/ 指向环（视偏差→ω_ref）    │
├──────────────────────────────────────────────────────────────────┤
│ 稳定层  │ ★ 速率稳定环（陀螺反馈 → ω_cmd）/ 增稳使能与旁路          │
├──────────────────────────────────────────────────────────────────┤
│ 运动层  │ 差速运动学（含镜像补偿）/ 限幅 / 速度整形                 │
├──────────────────────────────────────────────────────────────────┤
│ 协议层  │ Emm CAN 打包解包 / 校验 / 分包重组                        │
├──────────────────────────────────────────────────────────────────┤
│ 驱动层  │ TWAI / UART(IMU) / UART(视觉) / BLE(NimBLE) / LED / GPIO   │
├──────────────────────────────────────────────────────────────────┤
│ 硬件层  │ ESP32-S3 + CAN 收发器 + 汇电籽-601 模块 + 电机 + 电池     │
└──────────────────────────────────────────────────────────────────┘
```

**分层原则**：上层只通过定义好的接口调用下层，下层不反向依赖上层。
换手柄、换 IMU、换视觉源、换电机接口，都只影响对应的一层。

**关键点**：**稳定层是独立的一层**，它不知道自己上面是手柄还是视觉 ——
它只接受 `ω_ref`，输出 `ω_cmd`。这让"增稳开/关对比演示"（FR-18）
变成一行旁路开关，也让二期接视觉时不用动稳定层。

### 4.1.2 组件划分

```
esp32_turret/
├── CMakeLists.txt
├── sdkconfig.defaults            # 关键配置：TWAI / NimBLE(BLE central) / UART / PSRAM
├── main/

    ├── motor_can/                # Emm CAN 协议层（移植 tools/zdt_can.py）
    │   ├── emm_protocol.c/.h     # 打包 / 解包 / 校验 / 分包重组
    │   └── motor_can.c/.h        # TWAI 驱动 + 收发队列
    ├── imu_uart601/              # ★ 汇电籽-601 UART 帧解析 + 校验/超时 + 角度换算
    ├── stabilizer/               # ★ 速率稳定环 + 使能/旁路 + 自激保护
    ├── gimbal_kin/               # 差速运动学正解反解 + 镜像补偿 + 限幅
```

**移植要点**：`components/motor_can/emm_protocol.*` 是 `tools/zdt_can.py`
中 `build_frames()` / `reassemble()` 的 C 版本，帧格式已在 PC 端实测确认，
**逻辑照搬即可，不需要重新逆向**。

### 4.1.3 任务划分

| 任务 | 优先级 | 周期 | 职责 |
|---|---|---|---|
| `imu_task` | **最高** | **事件驱动（100 Hz，收帧触发）** | 解析 601 上报帧 → 校验/超时判定 → 原始值换算 → 写队列 |
| `stabilizer_task` | **最高** | **10 ms** | 速率稳定环：读陀螺 + `ω_ref` → 输出 `ω_cmd` |
| `safety_task` | 高 | 10 ms | 心跳超时、软限位、急停、IMU 异常、故障状态机 |
| `motor_tx_task` | 高 | **10 ms** | CAN 速度模式打包下发（两帧背靠背，无需同步广播） |
| `motion_task` | 中 | 10 ms | 模式状态机、**指向环**、差速反解、限幅 |
| `can_rx_task` | 中 | 事件驱动 | CAN 接收 → 队列（应答 / 到位 / 故障标志） |
| `gamepad_task` | 中 | 事件驱动（每收到一帧 notify） | 手柄 notify 帧 → 摇杆/按键状态（帧解析在 BLE 回调里完成，此任务只做映射） |
| `uart_comm_task` | 低 | 20 ms | 与泰山派收发、状态上报（二期） |

> **任务优先级设计的核心**：`imu_task` 与 `stabilizer_task` 必须是最高的两个。
> `imu_task` 不设固定周期，而是**由 UART 收帧中断唤醒**（模块固定 100 Hz 主动上报）；
> `stabilizer_task` 与它同拍，跑 10 ms。
>
> **ESP32-S3 是双核** —— 建议把这两个任务**绑定到 APP_CPU（核心 1）**，
> 把 BLE 协议栈放到 PRO_CPU（核心 0），避免无线协议栈的
> 长临界区阻塞稳定环。这是 ESP32-S3 做实时控制的关键实践。
>
> ⚠ **注意**：v1.1 时"把 UART 都放核心 0"的说法在本版本**不成立**了 ——
> 现在 IMU 也走 UART，而它是**控制通路**，必须留在核心 1 跟 `stabilizer_task` 同核。
> 放核心 0 的只有**与泰山派通信的那路 UART**（`uart_comm_task`）。

**任务间通信**：全部通过 FreeRTOS 队列，不使用全局共享变量跨任务直接读写。

- `imu_task` → `stabilizer_task`：陀螺数据队列（长度 1，覆盖式，**永远用最新样本**）
- `stabilizer_task` → `motor_tx_task`：电机指令队列（长度 1，覆盖式，**过期指令直接丢弃**）
- `motion_task` → `stabilizer_task`：`ω_ref` 队列（长度 1，覆盖式）
- `can_rx_task` → `safety_task` / 状态上报：应答队列

> **覆盖式队列是关键**：实时控制里"用最新数据"永远优于"处理完积压的旧数据"。
> 队列积压意味着相位滞后，是稳定环振荡的常见根因。

### 4.1.4 模式状态机

```
                   ┌────────────────────────────────────────┐
                   │                                        │
                   ▼                                        │
             ┌──────────┐   手柄连接 + 使能       ┌──────────┴────────┐
             │   IDLE   │────────────────────────►│      MANUAL       │
             │ 电机失能 │                         │ 摇杆 → ω_ref      │
             └────┬─────┘                         │ 增稳环可开/可关    │
                  │                               └─────────┬─────────┘
                  │                                         │  ▲
                  │                            模式切换键    │  │ 模式切换键
                  │                                         ▼  │
                  │                               ┌───────────────┐
                  │                               │     AUTO      │
                  │                               │ 视觉偏差       │
                  │                               │ → ω_ref       │
                  │                               └───────┬───────┘
                  │                                       │
                  └──────── 急停 / 故障 ◄──────────────────┘
                            （任意模式 → IDLE + 报警）
```

| 状态 | 电机 | `ω_ref` 来源 | 进入条件 |
|---|---|---|---|
| `IDLE` | 失能 | 无 | 上电、急停、故障、手柄未连接 |
| `MANUAL` | 使能 | 手柄摇杆 | 手柄已连接 + 显式使能 |
| `AUTO` | 使能 | 泰山派偏差 | AUTO 模式下泰山派心跳正常 |
| `FAULT` | 失能 | 无 | 堵转/过流/过热/低压/IMU 异常 → 需显式复位 |

**稳定环与模式的关系**：稳定环是**贯穿 MANUAL 与 AUTO 的公共层**，
不随模式切换而改变。模式切换改变的只是"谁提供 `ω_ref`"。

| 模式组合 | 行为 |
|---|---|
| MANUAL + 增稳关 | 纯速度跟随：摇杆给多少角速度，电机就走多少 —— **用于对比演示** |
| MANUAL + 增稳开 | 摇杆给期望角速度，陀螺环保证实际速率跟随并抗扰 —— **端起来走动时视轴保持指向** |
| AUTO + 增稳开 | 视觉给 `ω_ref` 锁定目标，增稳环抵消载体扰动 —— **真实光电转台的工作模式** |
| AUTO + 增稳关 | 纯视觉伺服 —— 抖动会被放大，仅用于对照 |

> **AUTO 降级（SR-02）**：AUTO 下泰山派心跳超时 → 若 IMU 正常则**降级为
> 惯性稳定保持**（视轴停在当前惯性指向，不随载体晃动）；若 IMU 也异常则退回 IDLE。
> **绝不在失去控制源时继续运动。**

## 4.4 控制回路（三层结构）

```
╔══════════════════════════════════════════════════════════════════╗
║  指向环（外环）                                                   ║
║  周期：33 ms（视觉 30 FPS）/ 10 ms（手柄）                        ║
║                                                                  ║
║  视觉模式：像素偏差(ex,ey) → PD + 前馈 + 低通 → (ω_ref_pan, ω_ref_tilt) ║
║  手动模式：摇杆值 → 死区 + 曲线 + 限幅        → (ω_ref_pan, ω_ref_tilt) ║
╚═════════════════════════════╦════════════════════════════════════╝
                              ║ ω_ref（覆盖式队列，永远取最新）
╔═════════════════════════════▼════════════════════════════════════╗
║  速率稳定环（内环）★ 增稳核心                                     ║
║  周期：10 ms（= IMU 上报率 100 Hz）                               ║
║                                                                  ║
║  ω_gyro  ←── 汇电籽-601 上报的角速度（模块已融合/校准，ESP32 滤波）║
║  ω_err = ω_ref − ω_gyro                                           ║
║  ω_cmd = ω_ref + Kv · ω_err        ← 陀螺反馈抵消载体扰动          ║
║                                                                  ║
║  旁路开关：Kv = 0 时退化为纯 ω_ref 跟随（用于开/关对比演示）      ║
╚═════════════════════════════╦════════════════════════════════════╝
                              ║ (ω_cmd_pan, ω_cmd_tilt)
╔═════════════════════════════▼════════════════════════════════════╗
║  运动层                                                           ║
║  差速反解（含 2 号镜像）→ 限幅 → 软限位检查 → ω1_cmd, ω2_cmd     ║
╚═════════════════════════════╦════════════════════════════════════╝
                              ║ CAN 速度模式 F6（单帧/电机，10 ms）
╔═════════════════════════════▼════════════════════════════════════╗
║  电机内部三环（X42S 自带，20 kHz）                                ║
║  电流环 / 速度环 / 位置环 —— 本项目不实现，只下发速度指令         ║
╚══════════════════════════════════════════════════════════════════╝
```

**带宽分层（v1.2 修正后）**：20 kHz（电机内部）≫ 100 Hz（稳定环）> 33 Hz（视觉指向环）。

⚠ **这里不再有"每一层比外面快 30 倍"的说法** —— v1.1 假设 IMU 1 kHz 采样时成立，
实物模块固定 100 Hz 上报后，**稳定环与视觉指向环只差约 3 倍**。
按采样定理，100 Hz 采样对应的可用闭环带宽约 `fs/10 ≈ 10 Hz`（见 PR-12），
而视觉环本身在 30 Hz —— **两者太接近，不能当作"严格分离"来设计**。

**应对方式**（见 6.8 与 8-R-21）：

1. **视觉环的输出必须重滤波**：像素偏差先低通再进 PD，把视觉环的有效带宽压到
   低于稳定环的穿越频率，用相位代价换稳定性
2. **稳定环增益（`Kv`）比原计划更保守**：相位裕度目标仍是 ≥ 30°（PR-14），
   但要在实际采样率下重新整定，不能沿用 1 kHz 假设下算出的值
3. **承认这是硬上限**：想真正做"高带宽增稳"必须换更高回报率的 IMU，
   与本方案的主控算力无关（见 6.1）

**为什么必须是"速率环 + 指向环"而不是单一位置环？**
位置环要等"发现偏了再纠"，对扰动是事后响应；速率环用陀螺做**阻尼反馈**，
能在偏差还没积累起来时就抑制掉扰动。**增稳的本质是提高阻尼，而不是提高增益。**

**为什么必须是"速率环 + 指向环"而不是单一位置环？**
位置环要等"发现偏了再纠"，对扰动是事后响应；速率环用陀螺做**阻尼反馈**，
能在偏差还没积累起来时就抑制掉扰动。**增稳的本质是提高阻尼，而不是提高增益。**

**一期实现的层级**：

| 层 | 一期 | 二期 |
|---|---|---|
| 指向环 | ✅ `ω_ref` 来自手柄摇杆 | ✅ `ω_ref` 来自视觉偏差 |
| 速率稳定环 | ✅ | ✅（不变） |
| 运动层 | ✅ | ✅（不变） |

> **注意**：一期的"指向环"在手柄模式下只是摇杆映射，不需要控制器；
> 但**接口与稳定层是分开的**，所以二期接视觉时只需替换 `ω_ref` 的来源。

**增稳环的控制律（一期内环）**：

| 输入 | 处理 | 输出 |
|---|---|---|
| 模块上报的角速度（转换后） | **零偏由模块内部标定**（ESP32 只监测漂移）+ 低通滤波（抗混叠 + 抑制结构振动） | `ω_gyro` |
| `ω_ref` − `ω_gyro` | 比例增益 `Kv`（必要时加积分消除稳态误差） | 速率修正量 |
| `ω_ref` + 修正量 | 限幅（不超过电机最大角速度） | `ω_cmd_pan`、`ω_cmd_tilt` |
| `ω_cmd_pan`、`ω_cmd_tilt` | 差速反解 + 镜像补偿 → 加速度限幅 → 软限位 | 最终 CAN 指令 |

> **滤波截止频率要重新定**：100 Hz 采样下，混叠频率只有 50 Hz，
> 结构性振动（齿轮啮合、电机斩波）很容易折进来。低通截止建议取
> **20–30 Hz 起调**，在"抑制混叠"与"保留相位裕度"之间取舍 —— 这是 M7 的核心难点。

# 5. 通信协议

## 5.1 ESP32 ↔ 电机（Emm CAN 协议，实测确认）

**物理层**：CAN 2.0B 扩展帧，**500 kbps**（实测），总线两端 120 Ω。

**帧格式（2026-09-16 实测确认）**：

```
扩展帧 ID = (地址 << 8) | 包号        包号从 0 开始
数据      = 功能码 + 参数 + 校验(默认 0x6B)
```

> ⚠ **地址只在 CAN ID 里，不要放进数据**
> —— 把地址写进数据里电机会返回 `EE`（命令格式错误）。这是历史踩过的坑。
> （`docs/01-上位机CAN调试入门指南.md` 中 CAN 章节"数据里带地址"的写法是错的。）

**长命令分包**（>8 字节按 7 字节一包，每包开头重复功能码）：

```
完整 = FD dir spdH spdL acc p3 p2 p1 p0 raF sync 6B        (12 字节)
第 0 包 = [FD] + 前 7 字节
第 1 包 = [FD] + 剩余字节
```

分包之间需留间隔（约 3 ms）防粘包。**注意：位置模式因分包 + 间隔而不适合高频下发，
这正是增稳环改用速度模式的原因（见 6.8）。**

**常用命令表（Emm 固件）**：

| 功能 | 功能码 | 字节数 | 说明 |
|---|---|---|---|
| 使能控制 | `F3 AB` | 5 | 使能/失能，支持同步标志 |
| **速度模式** | **`F6`** | **7** | **方向 + 速度 + 加速度 + 同步标志 —— 单帧，增稳环使用** |
| 位置模式 | `FD` | 12 | 方向 + 速度 + 加速度 + 脉冲数 + 运动模式 + 同步标志（需分包） |
| 快速位置模式 | `F1` + `FC` | 11 / 6 | 先设参数，之后只发 int32 脉冲（适合高频绝对定位） |
| 立即停止 | `FE 98` | 4 | 支持同步标志 |
| 触发多机同步 | `FF 66` | 3 | 广播地址触发 |
| 多电机命令 | `AA` | 变长 | 一条命令下发多个电机 |
| 读实时位置 | `36` | 3 | 返回 int48 |
| 读实时转速 | `35` | 3 | |
| 读状态标志 | `3A` | 3 | 使能 / 到位 / 堵转 |
| 读系统状态 | `43 7A` | 3 | 电压 / 电流 / 位置 / 转速 / 故障（`zdt_can.py` 有完整解码） |
| 触发回零 | `9A` | 变长 | 指定回零模式 |
| 设置单圈零点 | `93 88` | 4 | |
| 解除堵转保护 | `0E 52` | 3 | |

**主动上报**：到位 `FD 9F`、回零完成 `9A 9F`、夹紧 `F5 9F`

**回包结果码**：

| 码 | 含义 |
|---|---|
| `02` | 执行正确 |
| `12` | 已在零点/限位，电机不动 |
| `9F` | 动作完成 / 条件不符 |
| `E2` | 参数错误 |
| `EE` | 命令格式错误 |

**两台电机如何同步**：

| 场景 | 策略 |
|---|---|
| **增稳环运行（速度模式，100 Hz）** | **不需要同步广播** —— 两个速度帧背靠背发送（间隔 < 0.5 ms），速度指令立即生效，时间差远小于机械响应时间 |
| 绝对定位（位置模式，低频） | 多机同步标志（`snF=1` 缓存 → 广播 `00 FF 66 6B` 触发同时运动）—— 已在 PC 端验证有效 |
| 回零 / 大角度轨迹 | 用多电机命令（`00 AA len …`）一次发完，减少总线占用 |

> **为什么增稳环不需要同步广播**：位置模式下两个电机若不同时启动，
> 中间过程的姿态会偏离规划轨迹（因为 pan/tilt 是耦合的）；
> 而速度模式下每个电机独立跟随自己的期望速率，微小的时间差只产生
> 微小的姿态误差，且会在下一个周期被陀螺环修正掉。
> **这是"速度模式 + 高刷新率"相比"位置模式 + 同步广播"更适合增稳的根本原因。**

## 5.2 ESP32 ↔ IMU（UART，板内）

**物理层**：UART1，**GPIO17 = TX（→模块 R）**，**GPIO18 = RX（←模块 T）**，
**115200 8N1**（协议固定，不可改），模块**需要 5 V 供电**。

> 协议细节（帧结构、校验、全部指令、换算公式、自检脚本）单独整理在
> **`docs/02-601串口陀螺仪协议.md`** —— 与逆向工程里那份 Emm_V5 协议笔记同一性质：
> 都是从厂商文档还原出来的、可直接照着写代码的协议规格。

**帧格式**：

```
┌──────┬──────┬───────┬──────┬─────┬─────────┬──────┐
│ 0xAA │ 0x55 │ DevID │ CMD  │ LEN │  DATA…  │  CS  │
│  1B  │  1B  │  1B   │  1B  │ 1B  │  LEN B  │  1B  │
└──────┴──────┴───────┴──────┴─────┴─────────┴──────┘
CS = (DevID + CMD + LEN + ΣDATA) & 0xFF     DevID 默认 0x60，小端
```

**本项目用到的指令**：

| CMD | 名称 | 方向 | 载荷 | 说明 |
|---|---|---|---|---|
| `0x0B` | 设置上报模式 | ESP32 → 模块 | `mode(uint8)` | 上电初始化：设 `mode=0`（全数据） |
| `0x0A` | 启动/停止上报 | ESP32 → 模块 | `0x01`/`0x00` | **必须发这条模块才开始推数据** |
| `0x01` | 数据上报 | 模块 → ESP32 | 见下 | **模块主动上报，100 Hz，ESP32 只管收** |
| `0x10` | 重新校准 | ESP32 → 模块 | — | 上电静止时触发一次，或漂移超限时手动触发 |
| `0xF0` | ACK | 模块 → ESP32 | — | 下行指令的应答 |

> ⚠ **`0x0B` 和 `0x0A` 是两条指令，别只发一条**：`0x0B` 只设模式，
> **模块不会因此开始推数据**，必须再发 `0x0A 01` 启动上报。
> 这是实测/文档核对时最容易漏的一步 —— 漏了会表现为"模块一点数据都不来"，
> 很容易误判成接线或模块坏了。

**上报载荷（模式 0，`LEN=18`）**：

```
[ AccX, AccY, AccZ, GyroX, GyroY, GyroZ, Pitch, Roll, Yaw ]
   6 × int16 原始值（小端）            3 × 角度，×100 的整数：
                                        Pitch/Roll int16（−18000~18000）
                                        Yaw        uint16（0~36000）
```

**关键点**：

- **增稳环要的是 `GyroX/Y/Z`（角速度），不是姿态角** —— 姿态角是模块内部融合的结果，
  有额外延迟，拿来做速率反馈会白白吃掉相位裕度
- **不要轮询**：模块固定 100 Hz 主动推，主机发读命令只会打乱它的节奏
- **丢帧不会重发**：这是与 SPI 轮询最本质的区别 —— 主机没有"再读一次"的机会，
  所以**帧超时检测（SR-10）是必需的，不是可选的**
- **零偏由模块负责**：模块内部做温度补偿与零偏标定（FR-15）。
  ESP32 不重复做零偏估计，只**长期监测**上报值的均值是否漂移超限
- **ESP32 侧的滤波**：一阶低通或二阶 Butterworth，截止频率需在"抑制混叠/结构振动"
  与"相位滞后"之间折中。⚠ 100 Hz 采样下混叠频率只有 50 Hz，
  **截止建议从 20–30 Hz 起调**，不要沿用 v1.1 假设 1 kHz 时的 100 Hz

**初始化时序**（上电后）：

```
① ESP32 发 0x0B mode=0（全数据）  → 等 0xF0 ACK，超时 100 ms 重试，共 3 次
② ESP32 发 0x0A data=0x01（启动上报）→ 同样等 ACK，同样重试
③ 模块开始 100 Hz 上报，ESP32 校验帧头/长度/CS
④ 静止 2 s 采均值 → 若零偏残差 > 0.5 °/s（AC-10），发 0x10 重新校准
⑤ 进入正常闭环，`imu_task` 由收帧事件驱动
```

## 5.3 ESP32 ↔ 泰山派（UART 自定义协议，二期）

**物理层**：**UART2**（GPIO10/11 ⬜待上板确认），115200 8N1（可升至 921600）。
（UART1 已被 IMU 占用，见 5.2；GPIO10/11 是 v1.1 留给 IMU SPI 的引脚，现已释放）

**帧格式**：

```
┌──────┬──────┬──────┬──────┬───────┬───────┬───────────┬────────┐
│ 0xA5 │ 0x5A │ ver  │ type │ seq   │  len  │  payload  │ crc16  │
│  1B  │  1B  │  1B  │  1B  │  2B   │  2B   │   len B   │  2B    │
└──────┴──────┴──────┴──────┴───────┴───────┴───────────┴────────┘
CRC16（CCITT）覆盖 ver 至 payload 末尾；seq 用于去重与丢包统计
```

**消息类型**：

| type | 名称 | 方向 | 载荷 | 说明 |
|---|---|---|---|---|
| `0x01` | `SET_ERROR` | 泰山派 → ESP32 | `ex(int16) ey(int16) conf(uint8) t_ms(uint32)` | 归一化偏差 × 1000，范围 ±1000；`conf` 为置信度 0–100 |
| `0x02` | `HEARTBEAT` | 双向 | `seq(uint16) t_ms(uint32)` | 每 100 ms 一次，超时 500 ms 触发 SR-02 |
| `0x03` | `STATUS` | ESP32 → 泰山派 | `pan(int16) tilt(int16) mode(uint8) fault(uint8)` | 角度 × 100 |
| `0x04` | `SET_MODE` | 双向 | `mode(uint8)` | 请求切换模式 |
| `0x05` | `ESTOP` | 双向 | — | 立即停机 |
| `0x06` | `TARGET_LOST` | 泰山派 → ESP32 | — | 目标丢失，ESP32 执行降级策略 |
| `0x07` | `SET_STAB` | 双向 | `enable(uint8)` | 请求开关惯性增稳环（用于演示与调试） |

**吞吐估算**：`SET_ERROR` 约 24 字节，20–30 FPS 下约 720 B/s，
115200 baud（≈11.5 kB/s）**余量充足**，无需提高波特率。

## 5.4 ESP32 ↔ 手柄（BLE 自定义协议，非 HID）

> ⚠ **本节在 v1.3 被完整重写。** v1.2 及以前假设手柄是标准 BLE-HID、用 `esp_hid_host` 连接 ——
> **这个假设被实物推翻**：手柄是 **CodexPad-S10**，官方明确声明**它不是 BLE-HID 设备**，
> 不会被操作系统当成标准游戏手柄，必须自己建立 GATT 连接并解析厂商自定义二进制帧。

**角色与协议栈**：ESP32 作为 **BLE 主机（NimBLE GATT 客户端）**主动连接手柄；
**不使用 `esp_hid_host`**（那是连 HID 设备的组件）。

**GATT 结构**：

| 服务 | UUID | 特征 | UUID | 用途 |
|---|---|---|---|---|
| **输入服务** | **`0xFFA0`** | **输入特征** | **`0xFFA1`** | **notify，输入数据流全在这里** |
| 设备信息 | `0x180A` | 型号 / 固件版本 | `0x2A24` / `0x2A26` | 连接后读取 |
| 电池 | `0x180F` | 电量 | `0x2A19` | 可选 |

**连接流程**（无需配对/绑定）：BLE 主机初始化 → 连接目标（BD_ADDR 直连或**按键掩码扫描**）
→ 读设备名/型号/固件 → `getService(0xFFA0)` → `getCharacteristic(0xFFA1)` → **写 CCCD 订阅 notify**。

**帧格式**（厂商 `robust_frame` 库）：`0xAA` + 转义载荷 + 转义 CRC8 + `0x55`；
转义符 `0xDB`、异或掩码 `0x20`（凡出现 `0xAA`/`0x55`/`0xDB` 都需转义）；
CRC8 参数 `poly 0x1D / init 0xFF / xorout 0xFF`（即 **CRC-8/SAE-J1850**，MSB-first）。

**载荷**（`gamepad_codec` 库）= 1 字节数据类型 + 8 字节状态，共 9 字节：

```
DataType=0x01 | buttons(u32 LE) | Lx | Ly | Rx | Ry
```

**按键位**：17 键（十字键 4 + □△✕○ + L1/L2/L3 + R1/R2/R3 + Select/Start/Home），
详见执行文档的位表。**摇杆 8 位，中心 `0x80`**。

**映射**：摇杆归一化到 `[-1.0, 1.0]`，经死区与灵敏度曲线后作为 `ω_ref` 交给指向环。
关键按键：**模式切换键（Start）**、**急停组合键（L1+R1+Start，SR-05）**、**增稳开关键（FR-18）**。

> ⚠ **两个必须记住的手柄硬件坑**（否则会浪费大量调试时间）：
> 1. **开机后 1 分钟内无设备连接会自动关机** —— 开发时最常踩的坑。
> 2. **长按 Home 键 3 s = 关机** —— 所以 **Home 键绝对不能做急停或任何功能键**。

> **额外收获**：手柄的**广播 Manufacturer Specific Data 里就带当前按键状态**，
> 所以可以**不连接就实现"按键掩码扫描连接"**（按住某组合键，主机只连按键状态匹配且 RSSI 最高的那台），
> 多手柄环境防误连、换手柄不用改代码。这也是 M2a 阶段的最小验证手段。

> **完整协议、位表、CRC 表、NimBLE 代码骨架、M2a–M2d 执行步骤与排错表**，
> 全部写在 **`docs/03-BLE手柄接入执行文档.md`**，本节不重复。

> ⚠ **这仍是整个一期风险最高的环节**，但风险性质已变：
> 从 v1.2 的"**协议未知、要按型号逆向 HID 描述符**"降级为
> "**移植工作量 + 两个待实测项**（摇杆物理方向与符号、实际 notify 帧率）"。
> 详见第 8 章 R-01 与第 7 章 M2。

# 6. 关键设计决策与取舍

> 本章是文档中**对面试最有价值的部分**。每个决策都写明备选方案与取舍理由。

## 6.1 为什么用 ESP32-S3 而不是原方案的 STM32H743？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **ESP32-S3** | 已有实物；双核 LX7 @240 MHz + 8 MB PSRAM；**内置 BLE**（手柄不用额外模块）；内置 TWAI；**双核可以专门绑一个核跑增稳环**；ESP-IDF 生态成熟 | 无紧耦合内存，中断延迟高于 M7；**多路 UART（IMU + 视觉）+ BLE + CAN 同时跑需要仔细的任务绑核** | ✅ **采用** |
| STM32H743 | M7 @480 MHz 实时性更强；适合 2 kHz 以上高带宽稳定环 | **无 BLE**（手柄要额外模块）；无 CAN 收发器；手上无实物 | 本期不用，保留为升级路径 |

**核心理由**：本项目三层控制里最内层（20 kHz 电流/速度环）**已经由 X42S 电机自己完成**，
ESP32 只需跑 **100 Hz** 的速率环 —— 这个负载对 240 MHz 双核而言相当轻松。
瓶颈不在算力，而在**链路长度与调试成本**。

> ⚠ **v1.2 修正**：v1.1 这里写的是"ESP32 只需跑 1 kHz 稳定环"，
> 换用 100 Hz 的 601 模块后**负载只有原来的 1/10**，选型理由变得更强，
> 但也说明**当前增稳环的瓶颈已经不在主控算力，而在 IMU 模块的 100 Hz 回报率**。
> 换成 M7 也提不高带宽，必须先换 IMU。

**升级路径**：若 M6/M7 后发现需要更高带宽的稳定环（例如换成直驱电机、
提升到 mrad 以下稳定精度），**第一步是换高回报率 IMU（≥ 1 kHz）**，
而非换主控；只有连"当前主控 + 高回报率 IMU"都不够时，
才把 ESP32-S3 降级为"手柄+通信协处理器"，将稳定环交给 STM32H743 ——
架构上已为此预留（见 4.1.1 的分层）。

## 6.2 为什么走 CAN 而不是 UART TTL 直连电机？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **CAN（+3.3V 收发器）** | 差分总线抗干扰强；两电机**共总线**靠地址寻址；**原生支持多机同步广播**；帧格式已在 PC 端实测确认，逻辑可直接移植 | 需采购一颗收发器（约几元）；占用 2 个 GPIO | ✅ **采用** |
| UART TTL | 不需要收发器，接线简单 | 需要**改电机通讯模式**；两电机共总线时 TTL 多点驱动易冲突；**没有硬件同步广播**；电平需确认 | ❌ |
| ESP32 做 USB 主机接现有 USB-CAN | 不用买硬件 | 要自己实现 gs_usb 协议，工作量最大且与项目目标无关 | ❌ |

**核心理由**：差速转台的两个电机由**同一套关节**耦合驱动，指令必须成对下发。
CAN 的差分总线 + 硬件同步广播 + **500 kbps 的余量**，支撑本项目 100 Hz 的双电机下发
**负载只有 5.2%**，还留了 20 倍余量给将来提速。

> ⚠ **v1.2 后这条理由也变弱了**：v1.1 写的是"500 Hz 下发、负载 26%"，
> 是当时的 1 kHz 稳定环倒推出来的。现在 100 Hz 下 CAN 早已不是瓶颈 ——
> **真正的理由是"硬件同步广播"这条能力**（位置模式下必须成对原子下发，见 5.1），
> 以及差分总线在电机斩波噪声环境下的抗干扰能力。这两条与速率无关，决策依然成立。

## 6.3 为什么用 ESP-IDF 而不是 Arduino / MicroPython？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **ESP-IDF** | **`twai`（CAN）、`nimble`（BLE 协议栈）、`uart` 都是官方组件**；FreeRTOS 任务/队列/绑核是一等公民；可精细配置优先级与栈；Kconfig 参数管理 | 上手曲线较陡 | ✅ **采用** |
| Arduino | 上手快、示例多；NimBLE-Arduino 也能做 BLE 主机 | 难以精确控制任务优先级与绑核，**100 Hz 控制环的确定性没保障**；混合框架体积大 | ❌（作为逃生路线保留） |
| MicroPython | 开发最快、可在线改；厂商有官方 `codex_pad_mpy_lib` 可快速验证链路 | **解释器无法保证 100 Hz 控制环的实时性**；非项目技术栈 | ❌（仅用于临时证伪） |

**核心理由**：本项目有两个硬需求 —— **BLE 主机**和**确定性控制环**。
⚠ **v1.3 修正**：手柄不是 HID 而是自定义 GATT 协议，这让"BLE 主机"这条门槛**降低了**
（NimBLE-Arduino 也能做，见 8.x 的备选路线），但**"确定性控制环"这条依然成立且是硬伤** ——
100 Hz 控制环要有确定的周期与优先级，Arduino 框架的调度做不到。
**所以决策结论不变，但理由从"BLE HID 只有 ESP-IDF 能做"改成了"实时确定性"**。

> 诚实标注：v1.2 把稳定环降到 100 Hz 后，"实时性不足"这条对 Arduino/MicroPython 的论据
> **确实被削弱了**（100 Hz 对它们并非不可能）。ESP-IDF 在此的真正优势是
> **任务绑核 + 优先级 + Kconfig 的一等公民支持**，以及协议栈行为可控。
> 这个权衡要主动讲出来，而不是假装对手做不到。

## 6.4 为什么跟踪控制律放在 ESP32 而不是泰山派？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **ESP32 收偏差自己闭环** | 泰山派卡顿/掉线不影响运动安全；控制周期稳定不受 Linux 调度抖动影响；限位、急停、模式切换、**稳定环**都在一个地方，状态一致；泰山派侧代码极简 | ESP32 侧代码稍多 | ✅ **采用** |
| 泰山派算好期望角度下发 | ESP32 代码简单 | Linux 调度抖动直接传导；**泰山派死机时转台拿着最后指令继续动**；且**增稳环只能在 ESP32**（陀螺接在 ESP32 的 UART 上），拆开会让两层环跨板通信，延迟与抖动都无法接受 | ❌ |
| 泰山派直接发 CAN 帧 | ESP32 几乎不参与 | 模式切换、限位、故障处理全部失效；两块板子抢总线 | ❌ |

**核心理由**：**增稳环必须在 ESP32** —— 陀螺模块接在 ESP32 的 UART1 上，
闭环绝不能跨板、跨 Linux 调度去做。既然稳定环在 ESP32，
那指向环也必须在 ESP32，否则"指向环（泰山派）→ 稳定环（ESP32）"这一跨板
链路会引入不可控的延迟抖动。

> ⚠ **这条理由在 v1.2 后变弱了**：稳定环从 1 kHz 降到 100 Hz，
> 而视觉指向环本身只有 30 Hz —— 两者相差约 3 倍，
> 跨板传输的抖动（Linux 上几十 ms 起）**相对 33 ms 的视觉周期仍然是可观的**，
> 所以结论不变；但要诚实承认，**"高带宽分离"这个理由已经不成立了**，
> 现在支撑这个决策的主要是**安全性**（泰山派掉线不失控）与**状态一致性**。

## 6.5 为什么泰山派用 UART 而不是 WiFi / USB？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **UART** | 延迟稳定无抖动；代码最少；泰山派 40pin 排针直接引出 | 需要一根线 | ✅ **一期采用** |
| WiFi / UDP | 无线 | 延迟抖动大；**与 BLE 共用射频前端，互扰会直接影响手柄与增稳环的稳定性** | 备选 |
| USB CDC | 有线，免接杜邦线 | 两端都要处理串口枚举、断连重连 | ❌ |

**核心理由**：**ESP32 的 BLE 与 WiFi 共用射频前端。**
手柄走 BLE 是刚需，而**增稳环对丢包和延迟抖动零容忍** ——
WiFi 协议栈的长临界区会抢占 CPU，直接破坏控制环的确定性。
所以泰山派链路避开 WiFi，用 UART。

## 6.6 为什么视觉模型训练延后，先用手工特征？

**核心理由**：数据采集 → 标注 → 训练 → RKNN 转换 → 部署，任何一步都可能耗掉好几天，
且**与"手柄→ESP32→CAN→转台"主链路 + "IMU→稳定环"的正确性无关**。
先用色块/形状等手工特征让整条链路跑通并验收，
之后替换识别模块时**链路代码一行不用改**（见 4.2 的模块解耦约束）。

这样安排的价值是：**永远不会出现"模型训不出来所以整个项目卡住"的情况。**

## 6.7 为什么 IMU 装在托盘（载荷）上而不是底座上？

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **装在托盘上，贴近视轴** | 陀螺**直接测量载荷角速率** → 反馈稳像，精度最高；是真实光电转台/吊舱的标准做法 | 线缆要跨旋转关节（需限制行程、中空轴或滑环）；增加托盘负载 | ✅ **采用** |
| 装在底座上 | 无走线问题；可测载体扰动做前馈 | 只能测到**载体**的扰动，要推算载荷姿态还需关节角，**推算误差直接进入控制回路**；本质是开环前馈，扰动抑制能力远低于反馈 | ❌ 单独使用 |
| 底座 + 托盘各一个（双 IMU） | 反馈 + 前馈结合，扰动抑制最优 | 成本翻倍，融合算法复杂度上升 | ⬜ FR-43，后续扩展 |

**核心理由**：**反馈优于前馈。** 装在托盘上，陀螺测的就是"视轴自己在怎么动"，
这是误差的直接测量；装在底座上，只能测"扰源在怎么动"，还需要模型推算
这个扰动对视轴的影响 —— 模型不准，补偿就不准。

**代价与应对**：线缆跨旋转关节 → 一期**先限制自转范围（如 ±90°）**验证增稳效果，
不引入新硬件。若后续要做连续自转，再评估滑环或中空轴方案（见 3.4.5）。

## 6.8 为什么增稳环用 CAN 速度模式而不是位置模式？

> ⚠ **本节在 v1.2 被完整重写。**
> v1.1 的唯一决定性理由是"位置模式在 1 kHz 下爆总线（120%）"。
> 增稳环降到 **100 Hz** 后，这个数字变成 **12%** ——
> **原来的论据不成立了，但结论没变，只是理由换了一套。** 下面重推。

**先看总线负载（500 kbps，512 位/ms）**：

| 方案 | 单周期帧数 | @100 Hz（本方案） | @1 kHz（若换 IMU） | 结论 |
|---|---|---|---|---|
| 位置模式 `FD` | 4 帧（2 包/电机） | 12% ✅ | **120% ❌ 爆总线** | ❌ 不可用于增稳 |
| 快速位置模式 `F1`/`FC` | 2 帧 | 5.2% ✅ | 52% ⚠ | 备选（需要绝对定位时） |
| **速度模式 `F6`** | **2 帧** | **5.2% ✅** | 52% | ✅ **采用** |

> **数字说明**：扩展帧按最坏位填充约 130 bit/帧估算（位置模式 ≈150 bit/帧）。
> 目标是总线占用 **< 10%**（PR-16）—— 100 Hz 下**三种方案全部达标**，
> **说明这个指标在本版本里已经不能用来区分方案了**。
> （数字与 2.2 的负载估算表一致，那边有逐帧的字节拆解。）

**v1.2 的理由（按重要性排序）**：

1. **控制结构 / 相位：再也无法靠"高频"掩盖积分滞后** ← **新的首要理由**
   增稳环输出的是**速率修正量**。用位置模式就必须把速率**积分**成位置增量，
   而纯积分器在穿越频率处贡献 **90° 相位滞后**。
   v1.1 时还能靠 1 kHz 的高采样率换来裕度；**100 Hz 下相位裕度本来就更紧张**
   （PR-14 要求 ≥ 30°），再叠一个 90° 滞后基本没有余量。
   **用速度模式是"说同一种语言"，不给环路额外塞相位滞后。**
2. **不需要同步广播**：位置模式下两电机必须同时启动否则轨迹偏离；
   速度模式各电机独立跟随自己的目标速率，微小时间差会在下一个周期被修正。
   注意这条在 v1.2 里**不再是"省带宽"的理由**（5.2% 本来就够），
   而是**少一个故障点、少一份时序复杂度**。
3. **无分包**：位置模式 12 字节要分 2 包，中间必须留 ~3 ms 防粘包间隔。
   100 Hz 下 3 ms 塞得进 10 ms 周期（**所以这条也不再是决定性的**），
   但多一次分包意味着多一次丢包重组的可能 —— 在"丢帧不重发"的增稳环里不值得。

**结论的稳健性**：这条决策**在两条时间线上都成立** ——
100 Hz 下靠控制结构（相位），1 kHz 下靠总线带宽（120% 爆）。
所以将来若升级 IMU 到 1 kHz，**不需要重新论证这个决策**。

**代价**：速度模式没有绝对位置基准，长时间运行会有累积位置漂移。
应对：**低频（如 1 Hz）穿插位置模式或读取实际位置做校正**，
形成"速度模式为主 + 位置模式校正"的双模式下发。

> 📌 **面试提示**：这是一个**"结论对、论据错"**的典型例子 ——
> v1.1 的论据（爆总线）在实物参数下失效，但因为重新推了一遍，
> 反而暴露出更本质的理由（相位裕度）。
> **不要继续引用"位置模式爆总线"这个数字去解释 100 Hz 的增稳环**，
> 那会是个硬伤；该引的是相位裕度。

## 6.9 为什么"增稳本质是提高阻尼"而不是提高增益？

这是本项目**最有技术含量的一句话**，值得展开：

- **纯位置环**（原方案）：等视觉发现目标偏了，再发位置指令去追。
  对扰动是**事后响应** —— 扰动已经让视轴偏了，才开始纠。
  且位置环增益一高就容易振荡（因为要等偏差积累）。
- **速率环 + 陀螺反馈**（本方案）：陀螺实时测出"视轴正在以多快速度偏转"，
  乘增益 `Kv` 后**反向叠加到速度指令上** —— 相当于给系统加了**粘性阻尼**。
  扰动刚要让视轴动起来，就被阻尼压住。

**物理类比**：位置环像"发现车偏了再打方向"；速率环像"装了稳定翼，
一有侧风就自动产生反向力矩"。后者响应更快、更平滑、增益可以更高而不振荡。

**这也解释了 PR-14 为什么要求相位裕度 ≥ 30°**：阻尼反馈对相位滞后敏感，
**采样延迟（100 Hz 下平均 5 ms，最坏 10 ms）+ 模块内部融合延迟 +
滤波延迟 + CAN 传输延迟 + 电机响应延迟**总和不能太大，
否则"阻尼"会变成"正反馈"，系统自激 —— 这就是 SR-11 保护的由来。

> ⚠ **v1.2 后这条链更紧了**：v1.1 假设 1 ms 采样（采样延迟可忽略），
> 现在**采样延迟本身就有 5 ms**（半个 10 ms 周期），在延迟预算里很显眼。
> 这也是为什么前面反复强调"**增稳环要用陀螺角速度，不要用模块输出的姿态角**" ——
> 姿态角多了一道内部融合滤波，延迟更大，会把本来就不宽的裕度再吃掉一块。

## 7.3 关于 MIL 仿真（从必做降级为可选，但增稳环需要频域分析）

v0.1 方案要求先用 MATLAB 做模型在环仿真。**本方案调整如下**：

**运动学部分：确认不需要仿真。**
差速运动学（`pan ∝ θ1−θ2`、`tilt ∝ θ1+θ2`）已通过实机验证，
`tools/gimbal.py` 就是可用的参考实现。

**增稳环部分：需要频域分析，但用 Python 而非 MATLAB。**
稳定环整定需要知道**被控对象的频率响应**（增益、相位随频率的变化），
否则只能靠试凑增益，很危险。建议：

1. 在 ESP32 侧实现**扫频激励**：给 `ω_ref` 叠加正弦，频率从 **0.5 Hz 扫到 40 Hz**
2. 用陀螺记录响应，通过串口导出数据

> ⚠ **扫频上限由采样率定，不能拍脑袋**：100 Hz 采样对应 Nyquist 频率 50 Hz，
> 所以扫到 **40 Hz** 就该停 —— 再往上测到的不是真实频响，而是**混叠后的假象**。
> v1.1 写的"扫到 200 Hz"是 1 kHz 采样时的数，现在不成立。
3. 在 PC 上用 **Python（`scipy.signal` + `control` 库）** 做频响辨识与 Bode 图
4. 根据 Bode 图选择 `Kv` 与滤波截止频率，留足相位裕度（PR-14）

**这样做的价值**：把"试增益试到不振荡"变成"看着 Bode 图选增益"——
这是区分"会调参"和"懂控制"的地方，也是面试里最能讲的一段。

**MIL 仿真（MATLAB/Simulink）仍为可选**：若 M7 后想进一步做模型预测或前馈补偿，
届时再引入。一期的"仿真"就是上面这套 Python 频响分析。

## 10.4 环境注意事项（已踩过的坑）

1. **pip 直连 pypi.org 会 TLS 断连（SSLEOFError）**，必须用清华镜像：
   `pip install -i https://pypi.tuna.tsinghua.edu.cn/simple <pkg>`
   已装：`python-can` / `pyusb` / `libusb-package` / `gs_usb`
2. **ZDT_CANable 同一时间只能被一个程序占用** —— 用 `zdt_can.py` 前先关掉
   `Y42_Emm_CAN_Tool` / `cangaroo`
3. **"电机无数据返回"的根因排查优先级**（历史实战总结）：
   ① 小屏不显示 + 蓝灯常亮 = 固件卡 bootloader，重刷
   ② 接线松紧 / 接触不良，重插压紧
   ③ 地址重复
   ④ `P_Serial` 必须 = `CAN1-MAP`
   ⑤ CAN_H / CAN_L 接反
   ⑥ 共地 + 120 Ω 终端电阻
4. **调试增稳环时务必先旁路再逐步加增益** —— 直接上高增益会瞬间自激，
   对齿轮机构是冲击载荷。用 FR-18 的旁路开关做开关对比，比盲目调参安全得多。
5. **IMU 要 5 V 供电，不要接 3.3 V** —— 模块规格是 4.5–5.5 V，
   拿 3.3 V 顶上可能表现为"时好时坏"而非直接不工作，最难排查。
   逻辑线（TX/RX）才是 3.3 V 电平、可以直连。
6. **串口调试先确认 TX/RX 是否交叉** —— 与 CAN 的"接反就完全无通信"不同，
   UART 接反同样是一个字节都收不到，但很容易被误判成"波特率不对"。
   另外注意：**模块是主动上报的**，所以只要上电就该有数据流，
   不需要先发命令 —— 这一点可用来快速区分"线的问题"还是"命令的问题"。
7. **手柄有两个坑会伪装成"代码 bug"**：① **开机后 1 分钟内无连接会自动关机** ——
   扫描调试时手柄突然灭了不是代码问题，短按 Home 重开；② **长按 Home 3 s = 关机** ——
   所以 Home 键不能做功能键，急停用 **L1+R1+Start 组合键**（SR-05）。
   排错时若"扫不到手柄"，先查这三条：手柄是否开机、是否已过 1 分钟、是否被手机/电脑连走了。

## 10.5 术语表

| 术语 | 说明 |
|---|---|
| pan | 托盘自转角（水平旋转） |
| tilt | 托盘俯仰角（向上为正） |
| **视轴稳定** | Line-of-Sight Stabilization，使视轴（光轴）在惯性空间中保持指向不变 |
| **惯性增稳** | 用陀螺/IMU 反馈抑制载体扰动，使载荷保持惯性指向 |
| **复合稳定** | 惯性稳定环（抗扰）+ 指向环（跟踪）的复合控制结构 |
| **速率稳定环** | 以角速率为反馈量的内环，本质是给系统加阻尼 |
| **指向环** | 决定"要指向哪里"的外环，输入来自视觉或手柄 |
| **回程间隙** | Backlash，齿轮反向啮合时的空程，增稳带宽的主要限制因素 |
| **陀螺零偏** | Gyro bias，陀螺静止时的非零输出，需标定扣除 |
| **相位裕度** | 控制系统稳定性的度量，过低会导致自激振荡 |
| **群延迟** | Group delay，滤波器/融合算法对信号整体的时延，直接吃掉相位裕度 |
| **混叠** | Aliasing，高于 Nyquist 频率（采样率一半）的信号被采样后伪装成低频信号 |
| **主动上报** | 模块按固定周期自行推送数据，主机不发送读命令（601 模块的工作方式） |
| **CS（校验和）** | 601 协议每帧的末尾校验字节，`(DevID+CMD+LEN+ΣDATA) & 0xFF` |
| **DevID** | 601 模块的设备地址，默认 `0x60` |
| Emm 固件 | ZDT 电机默认固件（无力矩模式），本项目所用 |
| X 固件 | ZDT 电机可选固件，支持力矩模式与力位混合 |
| snF | 多机同步标志（synchronize flag） |
| TWAI | ESP32 内置的 CAN 2.0 控制器（Two-Wire Automotive Interface） |
| **BLE central** | 蓝牙低功耗主机角色，主动扫描并连接从机（ESP32 连手柄时的角色） |
| **NimBLE** | ESP-IDF 内置的轻量 BLE 协议栈（ESP32 作 BLE 主机/从机均可用），替代 Bluedroid |
| **GATT / 服务 / 特征 / CCCD** | 蓝牙属性协议：服务（如 `0xFFA0`）下挂特征（如 `0xFFA1`）；写 CCCD 即订阅该特征的 notify |
