# 04 - ESP32 CAN 电机驱动（TWAI + Emm + 差速逆解）

**这篇是 `docs/01-CAN调试入门指南.md` 的 ESP32 侧姊妹篇。**
01 讲的是「PC 上位机怎么调电机」，这篇讲「ESP32-S3 自己怎么跟电机说话」，
也就是 `firmware/esp32_turret/main/motor_twai.c` 的来龙去脉。

> **读法**：
> - 只想把线接对 → 看 §1、§2。
> - 想改协议 / 加指令 → 看 §3、§4。
> - 通信不通、转台不动 → 直接跳到 §8 排错表。
>
> 所有结论都是**上板实测**得来（2026-09-20 相位 1~7 全通，2026-09-21 手柄驱动转台跑通）。
> 没有实测支撑的判断会在文里标明「未钉死」。

## 1. 接线（**先看这个，接错一切免谈**）

### 1.1 引脚

| 信号 | ESP32-S3 GPIO | 去向 |
|---|---|---|
| CAN TX | **GPIO 4** | 收发器 `T`（CTX） |
| CAN RX | **GPIO 5** | 收发器 `R`（CRX） |
| — | GPIO 43 / 44 | **绝对不能接外设**，见下 |

收发器是**直连，不像 UART 那样交叉**：`T → GPIO4`、`R → GPIO5`、`H/L → 电机总线`。

> ⚠ **GPIO43 / GPIO44 是 console UART**（`GPIO43=U0TXD 出`、`GPIO44=U0RXD 入`
> → CH340 → USB → COM 口）。烧录和 `idf.py monitor` 走的全是这条链。
> 把 CAN 收发器接上去的症状是**递进的、很有迷惑性**：
> - 轻则 esptool 握手过了、写第一块就断：`A fatal error occurred: The chip stopped responding.`
> - 重则连握手都握不上：`Download mode successfully detected, but getting no sync reply`
>
> **判据**：拔掉外设立刻就能烧录 = 就是接线。**烧录前拿不准就先拔掉外设。**

### 1.2 电机侧前置条件（和 01 指南一致）

| 项 | 要求 | 不满足的后果 |
|---|---|---|
| `P_Serial` 通讯端口复用 | 必须设成 `CAN1-MAP`（出厂默认 `UART`） | 怎么接都不通 |
| 两台地址 | 1 和 2（出厂都是 1，要在小屏上改一台） | 一起应答 → 总线冲突 → 收不到数据 |
| 120 Ω 终端电阻 | 总线最两端各一个（H-L 之间） | 500 kbps 下丢帧、偶然能通 |
| 共地 | USB 转 CAN / ESP32 / 电机供电共地 | 通信不稳定、时通时不通 |
| 电机供电 | 10–29 V、≥3 A | **USB 转 CAN 不给电机供电** |
| 波特率 | 500 kbps，两端一致 | 完全不通 |

**另外一条电机状态的前置条件**：掉电再上电后电机会回到**失能态**，
必须先发 `F3 AB 01` 使能。不使能的话速度指令发出去也没人动，
症状是「日志一切正常，转台就是不转」。

## 2. 一帧到底长什么样（Emm 固件）

```
      标准 CAN 帧                          扩展帧（Emm 用这个）
   ┌──────────────────┐            ┌──────────────────────────┐
   │ ID(11 bit)       │            │ ID(29 bit) = addr<<8|pkt │
   │ DLC(0~8)         │            │ DLC(1~8)                 │
   │ Data(0~8 B)      │            │ Data = 功能码+参数+0x6B  │
   └──────────────────┘            └──────────────────────────┘
```

**四条规则**（`motor_twai.c` 的实现依据）：

1. **一律扩展帧**（`ide = 1`），广播（`FF 66`）也是。
2. **地址只在扩展帧 ID 里**：`ID = (addr << 8) | 包号`，**数据里不放地址**。
   `addr = 0` 是广播地址。
3. **数据 = 功能码 + 参数 + 校验 `0x6B`**，校验是**追加在最后的一个固定字节**，
   不是对前面字节求和。
4. **载荷超过 8 字节要拆包**：
   - 第 0 包装前 8 字节；
   - 之后每包 7 字节，**开头重复一次功能码**，包号递增；
   - 包间隔 ≥3 ms，防粘包。

### 2.1 常用指令速查

| 功能码 | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `0x36` | 请求 `{36, 6B}` | 应答 `36 + 符号 + 位置4B大端 + 6B`（7 B） | 读实时位置；位置 0..65535 表示一圈 |
| `0xF3` | `F3 AB 01/00 00` | — | 使能 / 失能 |
| `0xF6` | `F6 <dir> <vel 2B大端> <acc> 00` | — | 速度模式，单位**纯 RPM**（0–3000） |
| `0xFF` | `FF 66`（广播，ID=0x0000） | — | 多机同步触发 |

> ⚠ **`0xF6` 的单位是纯 RPM**。X 固件 §5.3.6 那一版是 0.1 RPM 标度，
> **别混**——差了 10 倍，症状是"指令 6 °/s 电机疯转"。

### 2.2 位置 → 角度

Emm 固件位置是**一圈 65536 个计数**（不是 36000，也不是脉冲数）：

```
角度(度) = 位置 × 360 / 65536
```

所以毫度是 `位置 × 360000 / 65536`，`motor_read_pos()` 里用 64 位中间量避免溢出。

## 3. ⚠⚠ 最大的坑：请求帧会**自带**校验

`send_payload_addr()` 会把 `0x6B` **自动追加**到载荷末尾（见规则 3）。
这带来一个反直觉的后果：

> **请求帧本身已经带了 `0x6B` 的，必须走 `send_raw_frame()` 直接发原始帧，
> 不能再走 `send_payload_addr()`。**

`0x36` 读位置的请求就是 `{0x36, 0x6B}` 两个字节，校验已经在里面了。
第一版代码图省事走了 `send_payload_addr()`，电机实际收到的是：

```
发了 {36 6B}  →  send_payload_addr 又补一个 6B  →  总线上是 {36 6B 6B}
```

**症状极具迷惑性**：TWAI 节点建好了、日志一切正常、一帧都不报错，
但**什么都读不回来**——因为电机认为校验不对，**静默丢弃**，连错误都不回。

**判据**：请求帧的最后一个字节已经是 `0x6B` ⇒ 走 `send_raw_frame()`。

## 4. TWAI 驱动怎么写（ESP-IDF v5.5 `esp_twai_onchip`）

### 4.1 建节点

```c
twai_onchip_node_config_t cfg = {
    .io_cfg = { .tx = 4, .rx = 5, .quanta_clk_out = -1, .bus_off_indicator = -1 },
    .bit_timing = { .bitrate = 500000 },
    .tx_queue_depth = 4,
    .fail_retry_cnt = 0,
    .flags = { .enable_loopback = 0, .enable_self_test = 0 },   /* ← 见 §5.2 */
};
twai_new_node_onchip(&cfg, &node);
twai_node_register_event_callbacks(node, &cbs, NULL);
twai_node_enable(node);
```

发送是**阻塞式**的：`twai_node_transmit()` 之后再
`twai_node_transmit_wait_all_done()`，等这一帧真正上线。

### 4.2 接收：过滤必须做在 ISR 里

总线上一共两台电机在回话，**光凭功能码过滤会张冠李戴**
（1 号的 `36` 被当成 2 号的）。所以过滤条件是**功能码 + 地址双过滤**：

```c
if ((want_func == 0 || data[0] == want_func) &&      /* 0 = 不限 */
    (want_addr == 0 || (id >> 8) == want_addr)) {    /* 0 = 广播地址，天然通配 */
       拷数据; 置标志;
}
```

ISR 里只做「拷数据 + 置标志」，**不打印、不阻塞**；解码全留给调用任务。
不合要求的帧**就地丢掉**（帧已经从 FIFO 取走了），于是调用方可以安心
"一直等到想要的那一帧"，不怕被别的帧卡住。

过滤器**只对当次请求有效**，用完立刻清 `want_addr = 0`，别漏给下一次。

### 4.3 一轮收发的时序

```
设置 want_func/want_addr → 清 s_rx_got → 发请求
      → 轮询 s_rx_got（vTaskDelay(1)，上限 100 ms）
      → 清 want_addr → 校验应答 → 解码
```

超时值：`TX_TIMEOUT_MS 100`、`TX_DONE_MS 200`、`RX_TIMEOUT_US 100000`。
100 ms 是**上板实测够用**的值，正常情况是微秒级。

## 5. 三个只有接了电机才会发现的坑

### 5.1 CAN 节点**不收自己发出的帧**（协议规定，不是 bug）

单节点自检物理通路时，**不能拿「收到帧」当判据**。
正确判据是 `tx_err / rx_err / 累计总线错误 = 0`：
发送时硬件必须逐位监听总线，位没回来就报位错误。

### 5.2 `enable_self_test` ≠ `enable_loopback`

| 标志 | 含义 | 什么时候能开 |
|---|---|---|
| `enable_self_test` | 发送**不需要 ACK** | **总线上有真电机时必须关** |
| `enable_loopback` | 自发自收，不对外发线 | 只属于单节点自检 |

开着 self_test 等于「**自己给自己盖章**」——电机没接也能"通信成功"。
`motor_twai.c` 里两个都显式写 0，就是为了让"没接电机"这件事**在日志里现形**。

### 5.3 帧会丢，而且**不声不响**

相位 7 实测遇到过一轮 2 号电机的 `FD`（读速度）没收到
（Δ=+0.02°，指令 −10°），那一轮总线上同时有 `填充错误` / `仲裁丢失`。
重跑就好了。

**推论（对增稳环是硬约束）**：后面 100 Hz 连续发速度指令时
**必须加应答核对或看门狗**，否则"发出去电机没收到"会直接变成控制失效。

## 6. ⚠ 线程契约：全工程只有一个任务能碰电机

`motor_twai.c` 里**每一个函数都会阻塞**（`transmit` + `wait_all_done` +
分包时的 `vTaskDelay(3ms)`）。

而 NimBLE 的 host 任务是：

| 属性 | 值 |
|---|---|
| 名字 | `nimble_host`（不是 `app_main.c` 里传的那个函数名） |
| 绑核 | **核 0（PRO_CPU）**，`CONFIG_BT_NIMBLE_PINNED_TO_CORE=0` |
| 栈 | **4096 字节** |
| 优先级 | 21 |

在它里面发 CAN，轻则拖垮协议栈，重则**栈溢出**。

> **契约：只有 `pad_input.c` 的 `m2c_task` 允许调 `motor_twai.c`。**

由此派生出两条设计：

1. **掉线停车不在 GAP 回调里做**。DISCONNECT 回调里直接调 `motor_stop()`
   就违反契约。正确做法是回调里只调 `pad_input_center()` 把状态压回中位
   ⇒ `ω_ref` 归零 ⇒ 控制环下一拍自己算出"值变了" ⇒ 由它发 0 速度。
2. **`motor_bringup()` 必须在 `pad_input_init()` 之前**。控制环一跑起来就开始
   发速度指令，那会儿 TWAI 必须已经就绪，否则指令全被 `motor_ready()` 挡掉。

## 7. 差速逆运动学（世界角 ↔ 两台电机角）

机构是一对斜锥齿轮，两台电机**差速合成**出两个世界自由度。

### 7.1 正解（编码器 → 世界角）

```
θ_tilt = (θ1 + θ2) / 2      俯仰
θ_pan  = (θ1 − θ2) / 2      自转
```

2 号是**镜像安装**，所以世界角要先取反：
`w1 = p1`、`w2 = −p2`，再代入上式。

### 7.2 逆解（世界角速度 → 两台转速指令）

```
cmd1 =  ω_tilt + ω_pan
cmd2 =  ω_pan  − ω_tilt      /* 2 号镜像 ⇒ 相当于取反 ω_w2 */
```

**符号组自检**（和相位 6 位置模式实测逐条对上）：

| 指令 | cmd1 | cmd2 |
|---|---|---|
| 纯俯仰 | +V | −V |
| 纯自转 | +V | +V |

### 7.3 单位：全程定点

| 量 | 单位 | 类型 |
|---|---|---|
| 角度 | 千分之一度（mdeg） | `int32_t` |
| 角速度 | 千分之一度每秒（mdps） | `int32_t` |
| 电机转速 | 纯 RPM | `int` |

**为什么不用浮点**：`%f` 在本 IDF 配置（newlib-nano）下可能印不出来；
控制环里定点也更省心。转换一次做完、四舍五入：

```c
rpm = (mdps >= 0) ? (mdps + 3000) / 6000 : (mdps − 3000) / 6000;
```

> 角度打印也刻意绕开 `%f`：`fmt_deg()` 用 `"%s%d.%03d"` 拆整数和小数部分。
> ⚠ 它返回**6 格轮转缓冲**里的一个 —— 一条 `printf` 里要塞好几个值时
> 不会互相冲掉，但**同一次调用取两个值再打印就会踩到同一格**。

## 8. 发送策略：不是每拍都发

速度指令是**有状态的**（电机保持最后收到的转速），所以 `m2c_task` 的策略是：

| 时机 | 理由 |
|---|---|
| 第一次 | 上电先明确下一道"停车"，别让电机揣着上电残留的转速 |
| 数值变了 | 摇杆动了 |
| 每 200 ms 心跳 | 见下 |

**为什么不"变了才发"就够**：50 Hz 重发纯属浪费总线
（500 kbps 上 2×3 帧 / 20 ms 也吃不消，后面增稳环 100 Hz 还要用）。

**为什么必须留心跳**：总线会丢帧且不声不响（§5.3）。
丢一帧"停车" = 松手了转台还在转。200 ms 心跳 ⇒ 真丢了下一拍就补上，
最多多转 200 ms。

**发失败不更新已发送值** ⇒ 下一拍（20 ms 后）自动重试。

## 9. 排错表

| 症状 | 先查哪里 | 常见原因 |
|---|---|---|
| `twai_new_node_onchip 失败` | GPIO 占用 | 接到了 GPIO43/44（console UART） |
| 节点建好了，**什么都读不到** | §3 | 请求走了 `send_payload_addr()`，补出双 `0x6B` |
| 两台都读不到 | 地址 / 接线 | `P_Serial` 还是 `UART`；地址撞了；缺 120 Ω；没共地 |
| 只读一台 | 那台的地址 | 第二台没改成 2 |
| 读得到位置，但**转台不动** | 使能 | 没发 `F3 AB 01`（掉电后回到失能态） |
| 指令发了，某一轴没动 | §5.3 | 帧丢了，重跑；增稳环阶段必须加应答核对 |
| 转动方向反了 | §7.2 | 把对应轴取负即可，不用改结构 |
| 转速差了 10 倍 | §2.1 | `F6` 用错了标度（纯 RPM vs 0.1 RPM） |
| 日志正常但手柄一停就急停 | — | 这是**设计使然**：notify 是变化驱动的，见 03 文档 §6.1 |
| 位置模式收尾总差 ~0.5° | §10 | 到位窗口改不动，不影响速度模式主线 |

## 10. 已知遗留：位置到达窗口是死命令（已穷尽）

改位置到达窗口 `D1 07 <store> <窗口2B>` 在本机电机固件 **V2.0.4 上是死命令**。

穷尽过的形状变体（6 条，含「把当前值 0.8 原样写回」和「去掉辅助码」两种）
**全部回 `00 EE`**。同族指令 `D3 56`（改过热过流）回 `02 执行正确`，
说明**写机制本身是好的**，问题就在这条指令上。

⇒ 排除取值不在允许集、排除辅助码写错。唯一办法是用电机自己的 OLED 菜单
改 `PRWindow`。

**影响面**：只限位置模式的收尾残差（到位判据 = `|目标−实际| < 窗口`，
默认 0.8° ⇒ 冲过 ~0.5° 就宣布到位）。
**增稳主线走速度模式，压根没有到位窗口 ⇒ 不阻塞主线。**

## 12. 相位 1~7 自检固件实测记录

CAN 侧是**分相位**验的，每相位只验一件事，全通之后才把已验证的部分
抽成 `motor_twai.c`（所以模块里的 Emm 帧格式、拆包、`0x36`、`F6`、
差速逆解都是**跑过的代码**，不是纸上代码）。

| 相位 | 验什么 | 实测结果 |
|---|---|---|
| 1 | 片内回环（不接线） | 15 / 0（收/错） |
| 2 | GPIO4→GPIO5 跨引脚通路 | 发出去的位都读回来，零错误 |
| 3 | 真总线发 `36` 读位置 | 1 号应答 **+30.042°**，连读 3 次一致 |
| 4 | 位置模式点位控制 | 6 段往返净位移 **−0.686°**，方向全对 |
| 5 | 参数写诊断 | 6 条形状变体全回 `00 EE`（见 §10） |
| 6 | 差速 + 2 号镜像补偿 | 纯俯仰 Δ俯仰 **+10.34°** / Δ自转 +0.30°；纯自转反过来 |
| 7 | **速度模式差速逆解** | 纯俯仰实测俯仰 **+36.62°/s** / 自转 +0.33°/s；纯自转俯仰 −0.61°/s / 自转 **+37.29°/s** |

**相位 6 和 7 是两条独立证据**：位置模式走的是 `FF 66` 同步广播 + 缓存触发，
速度模式走的是 `snF=0` 立即执行。两条路径的符号组逐条对上，
才敢说逆解写对了。
